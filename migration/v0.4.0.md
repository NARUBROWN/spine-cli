# Spine CLI v0.4.0 호환 워크스페이스로 마이그레이션하기

기존 Spine 앱과 초기 CLI 생성 프로젝트를 CLI `v0.4.0`으로 검사하고 생성·실행할 수 있게 만드는 가이드입니다. LLM 에이전트는 현재 프로젝트를 조사한 뒤 해당하는 변경만 적용합니다. 업무 로직, 공개 API, 인프라 설정과 기존 등록을 보존합니다.

여기서 워크스페이스는 애플리케이션 작업 디렉터리를 뜻합니다. CLI의 설치·갱신 레시피는 단일 Go 모듈을 지원합니다.

| 항목 | 이 가이드의 목표 |
| --- | --- |
| CLI | `github.com/NARUBROWN/spine-cli@v0.4.0` |
| Go | `1.25.5` 이상 |
| Spine | `github.com/NARUBROWN/spine v0.6.0` |
| Echo 플랫폼 | `github.com/NARUBROWN/spine-echo-platform v0.1.0` |
| Echo | `github.com/labstack/echo/v5 v5.4.4` |
| 의존성 레시피 | `echo-v0.1.0-spine-v0.6.0` |
| HTTP 어댑터 계약 | `spine.http-adapter/v2` |

이전 내장 Echo 앱, adapter v1 개발 버전과 CLI `v0.3.0` 레시피에서 넘어오는 경우를 포함합니다. 아래 내용에는 프레임워크 API 변경과 초기 생성 규칙의 차이도 포함됩니다. 모두 CLI `v0.4.0`에서 처음 발생한 변경이라는 뜻은 아닙니다. 더 새로운 버전을 사용하는 프로젝트는 이 조합으로 낮추지 말고 해당 버전을 지원하는 CLI를 사용합니다.

## 1. CLI와 현재 프로젝트 조사

```sh
go install github.com/NARUBROWN/spine-cli@v0.4.0
spine-cli version
# spine-cli 0.4.0
spine-cli schema --json
spine-cli capabilities --json
spine-cli context --root <project-directory> --json
```

위 루트 패키지는 `spine-cli` 실행 파일을 설치합니다. `spine-cli update`는 CLI 실행 파일을 갱신하지 않습니다.

변경 전에 다음을 확인합니다.

- `git status`와 현재 diff를 확인하고 기존 사용자 변경을 보존합니다.
- `go.mod`의 module, Go 버전과 require/replace, `go.work`, vendor, GOFLAGS를 확인합니다.
- `spine.toml`과 entrypoint, 앱 생성 코드, 생성자·라우트·consumer·WebSocket·interceptor 등록을 읽습니다.
- 기존 HTTP 요청·응답, 상태 코드, 접근 정책과 관련 테스트를 확인합니다.

`--json` 출력의 바깥 스키마는 `spine.cli-result/v1`입니다. `ok`, `exit_code`, `error`와 함께 `result`를 읽습니다. 실패해도 진단이 `result`에 있을 수 있습니다. `spine.toml`이 없는 앱의 `context` 실패는 다음 단계에서 설정을 추가한 뒤 다시 확인합니다. 실패를 빈 정상 결과로 취급하지 않습니다.

`capabilities`의 `implemented:false` 기능이나 존재하지 않는 `spine-cli migrate` 명령을 가정하지 않습니다. 명령·옵션은 현재 `schema`와 [에이전트 작업 계약](../llms.txt)을 기준으로 합니다.

## 2. spine.toml과 레이아웃 결정

기존 설정이 있다면 실제 경로를 유지합니다. 설정이 없고 앱 구성을 `internal/application`으로 분리한다면 다음처럼 추가합니다. module은 실제 `go.mod`와 같아야 합니다.

```toml
module = "example.com/shop"
entrypoint = "."
composition = "./internal/application"
port = 8080
layout = "legacy"
platform = "echo"
```

- `entrypoint`는 main 패키지의 빌드 경로입니다. 예를 들어 기존 서버가 `cmd/server`에 있으면 `./cmd/server`를 사용합니다.
- `composition`은 앱 생성·등록을 분석하고 편집할 파일 또는 디렉터리입니다. 부분 runtime probe도 사용할 앱은 모듈 아래의 import 가능한 패키지 디렉터리로 분리합니다.
- 허용 key는 `module`, `entrypoint`, `composition`, `port`, `layout`, `platform`입니다. 앱별 DB·broker 설정은 앱 자체 설정으로 관리합니다. `platform`은 현재 `echo`만 지원하며, HTTP 없는 앱은 생략할 수 있습니다.
- `layout`을 생략한 기존 앱은 legacy로 동작합니다. 호환성을 위해 모든 앱의 파일을 이동할 필요는 없습니다.

새 프로젝트는 `layout = "layered-v1"`을 기본으로 생성합니다. 기존 앱은 생성기의 동작 차이를 확인한 뒤 레이아웃 전환 여부를 정합니다.

| 항목 | 기존 legacy | layered-v1 |
| --- | --- | --- |
| domain | 전용 생성기 없음 | `database/domain/` |
| DTO | 전용 생성기 없음 | `src/dto/` |
| repository/service/controller | 기존 `src` 및 현재 패키지 규칙 | `src/repository/`, `src/service/`, `src/controller/` |
| `--depends` | 같은 패키지의 파일 이름 | 모듈 기준 `package/path:Type` |
| controller/resource 생성 | 기본 GET 경로도 등록 | HTTP 메서드와 경로를 별도로 등록 |
| resource | `src/<name>`의 세 구성 요소와 GET 경로 | domain, repository, service, controller 조합 |
| slice | 명시적인 `--storage memory`만 지원 | 지원하지 않음 |

layered-v1으로 전환할 때는 파일 이동과 Go package/import, 생성자 참조와 모든 등록을 함께 고칩니다. 경로는 `src/route/route.go`의 `Register(app spine.App) error`로 모으고 composition에서 반환 오류를 확인합니다. 실제 구성을 맞춘 뒤 `layout`을 변경합니다. 설정값만 바꾸면 기존 파일이 이동하거나 등록이 변환되지 않습니다.

레이아웃 전환 뒤 의존성 참조의 예는 `--depends src/repository/account:UserRepository`입니다. 전체 module path나 이전 파일 이름을 전달하지 않습니다. domain·DTO는 DI에 등록하지 않으며, resource 생성으로 DTO나 HTTP 경로가 생긴다고 가정하지 않습니다.

## 3. 앱 생성과 실행 분리

CLI가 분석할 수 있는 명시적인 앱 생성·등록을 composition에 두고, 서버 실행은 entrypoint에 둡니다. 기본 생성 프로젝트의 `BuildApplication` 반환형은 `(spine.App, boot.Options, error)`입니다.

아래는 `internal/application/application.go`의 최소 실행 예입니다. 기존 앱에 적용할 때는 기존 생성자·라우트·consumer·WebSocket·interceptor와 boot 옵션을 이 구조에 합칩니다. 예제 health 등록으로 기존 앱 전체를 대체하거나 같은 경로를 중복 등록하지 않습니다.

```go
package application

import (
    "os"

    "github.com/NARUBROWN/spine"
    platform "github.com/NARUBROWN/spine-echo-platform"
    "github.com/NARUBROWN/spine/pkg/boot"
    "github.com/NARUBROWN/spine/pkg/httpx"
)

type HealthController struct{}

func NewHealthController() *HealthController { return &HealthController{} }

func (*HealthController) Get() httpx.Response[map[string]string] {
    return httpx.Response[map[string]string]{Body: map[string]string{"status": "ok"}}
}

func BuildApplication() (spine.App, boot.Options, error) {
    app := platform.New()
    app.Constructor(NewHealthController)
    app.Route("GET", "/health", (*HealthController).Get)

    address := ":8080"
    if port := os.Getenv("SPINE_PORT"); port != "" {
        address = ":" + port
    }
    return app, boot.Options{Address: address, HTTP: &boot.HTTPOptions{}}, nil
}
```

`main.go`는 생성 결과를 검증한 뒤 실행합니다. import의 `example.com/shop`을 실제 module로 바꿉니다.

```go
package main

import (
    "log"

    "example.com/shop/internal/application"
)

func main() {
    app, options, err := application.BuildApplication()
    if err != nil {
        log.Fatal(err)
    }
    if err := app.Validate(options); err != nil {
        log.Fatal(err)
    }
    if err := app.Run(options); err != nil {
        log.Fatal(err)
    }
}
```

`BuildApplication` 안에서 `Run`, `RunContext`나 listener를 시작하지 않습니다. 분석기가 인식하는 `app := platform.New()` 같은 생성식을 사용하고 등록을 명시합니다. 임의 factory 함수나 해석하지 못하는 조건 뒤에 등록을 숨기면 `analysis_complete: false`가 될 수 있습니다. `boot.Options`도 반환하는 구조체 리터럴에서 HTTP 활성 여부를 확인할 수 있게 구성합니다.

HTTP 없는 워커는 `app := spine.New()`와 HTTP가 nil인 옵션을 유지합니다. 이 경우 Echo를 붙이거나 HTTP를 활성화할 필요가 없으며, 아래 Echo 전용 갱신 레시피를 그대로 적용하지 않습니다.

## 4. HTTP adapter v2 API 변경

### HTTP 플랫폼을 명시적으로 선택

이전 내장 Echo 앱의 `spine.New()`는 `platform.New()`로 바꿉니다. Spine `v0.6.0`의 `spine.New()`는 HTTP 플랫폼을 선택하지 않습니다. HTTP를 활성화하면서 factory를 빠뜨리면 검증·실행에 실패합니다.

| 기존 코드 | 목표 코드 |
| --- | --- |
| HTTP 앱의 `spine.New()` | `platform.New()` |
| `spine.NewWithHTTPAdapter(platform.NewFactory())` | `spine.New(spine.WithHTTPAdapter(platform.NewFactory()))` |
| `spine.New(platform.Option())` | 그대로 사용 가능 |
| `spine.Prepare(ctx, app, options)` 또는 `ApplicationPreparer` 검사 | `app.Prepare(ctx, options)` |
| `app.Transport(func(any))`와 `Config.NativeHooks` | `platform.WithEcho(func(*echo.Echo))` |

`app.RegisterTransport(...)`는 별개의 사용자 정의 transport 등록 API입니다. 제거된 `App.Transport`와 혼동해 삭제하지 않습니다.

### Native Echo 설정은 WithEcho로 이동

Echo v4 import를 `github.com/labstack/echo/v5`로 바꾸고 native handler·middleware의 인자를 `*echo.Context`로 변경합니다.

```go
app := platform.New(platform.WithEcho(func(e *echo.Echo) {
    e.GET("/native", func(ctx *echo.Context) error {
        return ctx.String(200, "native")
    })
}))
```

이 조각은 composition의 앱 생성식을 대체하는 예이며 `platform`과 `github.com/labstack/echo/v5` import가 필요합니다. 기존 native 경로·middleware 설정을 callback으로 옮깁니다. v5의 `HTTPErrorHandler`는 `func(ctx *echo.Context, err error)`이고 logger는 `log/slog`입니다. 경로 인자는 `PathValues()`를 사용하며 `Response()`는 `http.ResponseWriter`를 반환합니다. 응답 상태를 읽는 확장은 `echo.UnwrapResponse`를 사용합니다.

CLI는 `WithEcho` 생성식은 인식하지만 callback 안의 native 경로를 분석하거나 실행하지 않습니다. native 경로는 Spine의 HTTP interceptor, 본문 제한과 응답 staging을 거치지 않으므로 기존 접근 정책을 직접 검증합니다.

### 커스텀 어댑터·실행 컨텍스트·후처리 훅이 있는 경우

해당 인터페이스를 직접 구현하거나 내부 상태 key를 사용한 코드에만 적용합니다.

| 이전 계약 | v2 계약 |
| --- | --- |
| `ResponseWriter.WriteJSON(int, any)` | `WriteJSON(int, json.RawMessage)` |
| `ctx.Set/Get("spine.response_writer", ...)` | HTTP 전용 `core.HTTPResponseContext`의 `ResponseWriter`/`SetResponseWriter` |
| `ctx.Set("spine.params"/"spine.pathKeys", ...)` | `ExecutionContext.SetRoute(params, pathKeys)` |
| `PostExecutionHook.AfterExecution(ctx, results, err)` | 성공 후처리 `AfterExecution(ctx)` |

사용자 `Set/Get` 저장소는 계속 사용할 수 있지만 프레임워크 writer나 경로 상태를 바꾸지 않습니다. WS·consumer에 HTTP writer 인터페이스를 요구하지 않습니다. 사용자 Echo JSONSerializer는 원래 DTO 대신 `json.RawMessage`를 처리해야 합니다. 훅의 기존 오류 처리 로직은 새 성공 후처리에서 실행된다고 가정하지 말고 호출 경로를 검토합니다.

Prepare 기반 테스트·외부 서버 코드는 반환한 준비 결과의 `Handler()`를 연결하고 `Close(ctx)`로 정리합니다. HTTP가 꺼져 있으면 Handler는 nil입니다. Prepare는 listener를 열지 않지만 설정에 따라 broker readiness나 custom Init을 실행할 수 있습니다. 외부 서버의 listener는 호출자가 종료합니다.

## 5. HTTP 핸들러를 현재 계약에 맞추기

현재 CLI의 route 생성과 계약 검사는 기본 인자 resolver와 성공 반환형을 확인합니다. 예전 코드가 컴파일되더라도 요청 DTO를 값으로 받거나 raw DTO·slice·string을 반환하면 계약 검사가 실패할 수 있습니다.

```go
// 변경 전: 값 DTO 인자와 raw DTO 반환
func (*ProductController) Create(req CreateProductRequest) (ProductResponse, error)

// 변경 후: 본문 DTO 포인터와 HTTP 응답 wrapper
func (*ProductController) Create(req *CreateProductRequest) (httpx.Response[ProductResponse], error)
```

위 코드는 시그니처 비교입니다. 실제 메서드 본문은 기존 검증·업무 로직을 보존하고 성공 값을 `httpx.Response[ProductResponse]{Body: result}`로 감쌉니다. 명시한 상태 코드는 `Options: httpx.ResponseOptions{Status: 201}`처럼 유지합니다. 오류 반환 시에는 `httpx.Response[ProductResponse]{}, err`를 반환합니다. 파일·리다이렉트는 각각 `httpx.Binary`, `httpx.Redirect`를 사용합니다.

경로 인자는 `path.Int` 같은 Spine wrapper를 값으로 받습니다. 모든 인자를 포인터로 일괄 변환하지 않습니다. HTTP 오류는 `error`로 반환하며, 구체적인 구현은 [첫 HTTP API 예제](../internal/cli/first_api.md)를 참고합니다. 외부 타입·커스텀 resolver가 미해결이면 해당 확장과 분석 한계를 조사합니다.

## 6. 소스 수정 후 의존성 갱신

Echo 앱은 설정과 소스를 위 계약에 맞춘 뒤 프로젝트 루트에서 실행합니다.

```sh
spine-cli update --dry-run --json
spine-cli update --if-match <base_hash> --json
```

두 번째 명령의 `<base_hash>`에는 첫 결과의 `result.base_hash`를 사용합니다. 적용 전에 `result.changes`, `result.diff`, `result.selected_modules`와 검사 `stages`를 검토합니다. 입력을 다시 수정했다면 dry-run부터 새로 실행합니다.

`update`는 임시 복사본에서 의존성 해석, `go mod tidy`, 선택 모듈 검사, 정적 계약과 entrypoint 빌드를 수행하고 성공한 `go.mod`/`go.sum`만 반영합니다. 소스·디렉터리·설정은 마이그레이션하지 않습니다. 이전 API로 빌드가 실패하면 `failed_stage`와 `cause`, diagnostics를 보고 소스를 고친 뒤 다시 계획합니다. 앱 초기화·테스트·서버 실행은 이 단계에 포함되지 않습니다. dry-run도 네트워크와 Go 캐시를 사용할 수 있습니다.

활성 Go workspace가 있다면 `GOWORK=off`로 두 명령을 같은 환경에서 실행합니다. vendor, local replace, 사용자 지정 GOFLAGS와 symlink 입력은 지원 범위 밖입니다. 먼저 실제 사용 이유를 조사해 별도로 처리하고, 통과시키기 위해 일괄 삭제하지 않습니다. Echo 레시피가 맞지 않는 워커·커스텀 플랫폼은 필요한 공개 의존성을 별도로 고정하고 해당 구성으로 검증합니다.

새 앱을 만드는 경우는 기존 앱에 `new --force`를 실행하는 대신 빈 경로에서 생성합니다.

```sh
spine-cli new shop-api --module example.com/shop --dry-run --json
spine-cli new shop-api --module example.com/shop --if-match <base_hash> --json
```

오프라인으로 파일만 계획·생성하려면 두 명령 모두에 `--skip-install`을 붙입니다. 이 경우 생성 후 `go mod tidy`와 아래 검증이 필요합니다. 설치 생략 계획의 hash를 설치 포함 적용에 재사용하지 않습니다.

## 7. 계약·로컬 검증과 실제 동작 확인

변경한 Go 파일에 `gofmt`를 적용한 뒤 다음 순서로 실행합니다. 이후 명령은 프로젝트 루트 기준이며 다른 위치에서는 `--root <project-directory>`를 붙입니다. 등록에 환경변수를 사용한다면 검사와 실제 실행에 같은 값을 전달합니다.

```sh
spine-cli context --json
spine-cli contract check --json
spine-cli verify --json
```

완료 조건은 다음과 같습니다.

- `contract check`: envelope `ok: true`, `result.valid: true`, `result.analysis_complete: true`, `result.error_count: 0`을 확인합니다. warning도 검토하고 기존 CI가 strict라면 `--warnings-as-errors`를 유지합니다.
- `verify`: 정적 계약과 gofmt·vet·test 단계가 실제로 통과해야 합니다. 애플리케이션 테스트는 코드·인프라를 실행할 수 있습니다.
- 필요한 consumer·WebSocket 대조는 `spine-cli contract probe --json`으로 추가합니다. 이는 BuildApplication·Validate와 공개 registry를 실행하는 부분 검증이며 HTTP·DI·interceptor 실행 전체를 증명하지 않습니다.
- 앱을 `spine-cli dev`로 실행하고 다른 터미널에서 기존 대표 요청을 확인합니다. 위 최소 앱과 새 기본 프로젝트는 `curl -i http://localhost:8080/health`가 HTTP 200과 `{"status":"ok"}`를 반환해야 합니다. 기존 앱은 실제 경로·포트로 성공·오류 응답과 native 경로, 필요한 WS·DB·broker 동작도 확인합니다.

기존 snapshot이 있다면 검토 전에 덮어쓰지 않습니다. 현재 계약 payload는 `spine.contract/v1alpha2`이고 바깥 CLI envelope는 `spine.cli-result/v1`을 유지합니다. 이전 payload 스키마의 snapshot은 diff가 거부할 수 있습니다. 이전 파일과 `spine-cli inspect --json`의 등록을 비교해 의도한 변경인지 확인한 뒤 기준을 다시 저장합니다.

```sh
spine-cli contract snapshot --force
spine-cli contract diff --against spine.contract.json --json
```

기존 snapshot 경로가 다르면 snapshot에 `--output`, diff에 `--against`로 같은 경로를 지정합니다. `contract snapshot`은 `--json`, `--dry-run`, `--if-match`를 지원하지 않습니다. snapshot을 다시 썼다는 사실만으로 마이그레이션이 검증되지는 않습니다.

## 자주 발생하는 진단

| 진단 | 확인할 변경 |
| --- | --- |
| `spine.toml is required` | 실제 앱 루트와 설정 파일 확인 |
| `HTTP_ADAPTER_MISSING` | HTTP 활성 앱에 `platform.New()` 또는 명시적 factory 연결 |
| `HTTP_ADAPTER_API_REMOVED` | `NewWithHTTPAdapter`를 `New(WithHTTPAdapter(...))`로 변경 |
| `HTTP_NATIVE_HOOK_API_REMOVED` | `App.Transport` 설정을 `platform.WithEcho`로 이동 |
| `HTTP_ADAPTER_UNRESOLVED` | 인식 가능한 생성식·옵션을 사용하고 임의 factory/가변 옵션 조사 |
| `HTTP_CONFIGURATION_UNRESOLVED` | 반환하는 `boot.Options.HTTP`와 옵션 변수 변경 경로 확인 |
| `MODULE_GRAPH_UNAVAILABLE` | 모듈 버전·캐시·체크섬 확인, 의존성 갱신 또는 필요한 tidy 수행 |
| `HTTP_PARAMETER_BINDING_UNSUPPORTED` | 본문 DTO 포인터와 경로 인자 wrapper 확인 |
| `HTTP_RETURN_TYPE_UNSUPPORTED` | raw 반환값을 지원 HTTP 응답 타입으로 변경 |
| stale `base_hash` / `CONFLICT` | 새 dry-run을 만들고 diff 검토 후 새 hash로 적용 |

에이전트의 완료 보고에는 변경 파일·API, 유지하거나 전환한 layout, 실제 선택 모듈, 통과한 정적/로컬 검사와 실제 요청 결과를 기록합니다. 미실행 항목과 실패 원인을 함께 남기고, 정적 검사만으로 배포·외부 인프라까지 호환된다고 보고하지 않습니다.

더 자세한 프레임워크 변경은 [Spine v0.6.0 HTTP 플랫폼 전환 안내](https://github.com/NARUBROWN/spine/blob/v0.6.0/docs/migration/http-adapter-modules.md), 플랫폼 옵션은 [Echo 플랫폼 v0.1.0](https://github.com/NARUBROWN/spine-echo-platform/tree/v0.1.0)을 참고합니다. CLI 레시피와 생성식 지원 여부는 이 저장소의 현재 구현과 `capabilities`를 우선합니다.
